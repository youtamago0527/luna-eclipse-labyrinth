# 深層・数値境界の読み取り監査

対象：Assets/Scripts/Progression。コード変更、Unity起動、実セーブ操作なし。

## 通常プレイ

現在の有効遺物・通常保存から整数オーバーフローを起こす経路は見つからなかった。品質と倉庫Lvは999、バッグLvは20。品質補正は999、倉庫1019、バッグ40なので通常範囲で安全。満腹耐久と羅針盤は未確定上限だが、自動遺物付与自体が無効で、現在Lvが自然に巨大化する導線はない。

## 防御済み

- GetBonusの乗算はlong。加算はSafeSumでint上限手前1024に飽和し、基礎値加算の余白を残す。これは実装上の数値防御で、ゲーム上の階数上限ではない。
- Lv+1はint.MaxValueで停止。表示の現在値・次Lv値もlong計算。
- CompleteRunの20階刻みループはlong。開始階+間隔でint周回して無限ループになる問題は避けている。
- 開始階選択の++はselected<maxの場合のみ、--はselected>1の場合のみ。
- 倉庫・バッグ移動のindexは負数／Countを検査。容量判定は比較であり加算オーバーフローしない。

## 破損保存・異常入力の課題

1. **StoredItem.Enhancement**：int全域を保持する。Progression内部の表示／コピーは安全だが、Coreへ持ち込むと装備補正+1や攻撃基礎値の加算がint演算ならint.MaxValueで負に回る。通常生成の値では起きない。最小対処はCoreの効果計算をlong中間値＋範囲検証にすること。過去品の負強化値を理由なく0へ丸めない。
2. **極端に深いCompleteRun**：maxFloor=int.MaxValue、startFloor=1では約1億件の報酬機会を生成しメモリを消費する。整数オーバーフローではない。現在の通常プレイでは現実的でないが、将来の巨大深層／壊れた入力対策として報酬機会の区間圧縮またはページ生成が望ましい。ゲーム階数を100Fなどで打ち切る修正は不要。
3. **UIリスト高さ**：Resultsのrewards*100、Warehouseのrows*108はint乗算。数千万行を含む改変保存で桁あふれし得るが、メモリ／UI生成負荷が先に問題となる。通常操作の即時ブロッカーではない。長期対応は仮想化リストとページ表示。
4. **RelicBonusの公開可変フィールド**：サービスGetBonusから返る値は飽和済み。外部でBagBonus等へint.MaxValueを直代入すると派生容量の20+値はint桁あふれし得る。現LunaAppはそのような変更をしていない。将来APIを不変値にするか派生プロパティをlong中間値にする余地がある。

## 境界契約

『人工的な階層上限を設けない』と『intは有限』は別事項。階数の数値型の上限を越える操作は保存前に検知して明示エラーにするか、型移行する。階数int.MaxValueでのCore Floor++はProgression所有外なので親担当が確認する。通常プレイの到達目標として低い固定上限を新設する必要はない。

今回の優先提案は装備効果計算のlong化のみ。深層区間圧縮・リスト仮想化は将来の規模対応として扱う。

## build11での修正・検証追記

前段の装備強化値に関する指摘は修正済み。親担当がDungeonRunのAttackPower／DefensePower／SatietyIntervalをlong中間値で計算し、intの有効範囲へ飽和させた。通常の数値・バランスは変えていない。

GameplayContentTestsにint.MaxValue／int.MinValueの装備補正と満腹間隔の検査を追加し、build11で7組すべて成功したと親担当から報告された。深層の区間圧縮、巨大リストの仮想化など、残る将来課題は上記のとおり。
